# Замеры хранилища Verfix на одном хосте

В первом сравнении бот сохраняет байты в SQLite или в отдельном локальном каталоге. Во втором сравнении SQLite и PostgreSQL используют один способ хранения. [Спецификация #37](https://github.com/verf1x/telegram-agent/issues/37) · [Файлы #29](https://github.com/verf1x/telegram-agent/issues/29) · [СУБД #36](https://github.com/verf1x/telegram-agent/issues/36)

## Как повторить

Нужны Linux с cgroup v2, Node.js 26, Docker и `findmnt`. Запускай команды от обычного пользователя с доступом к Docker. По умолчанию стенд создаёт каталоги на том же накопителе, что и рабочая копия. `--data-root` задаёт другой существующий каталог для обеих БД и файлов. Стенд поднимает отдельный контейнер с привязкой к loopback и временным паролем. Для него достаточно Docker с локальным демоном.

```sh
npm ci
node scripts/bench-issue-37-storage.mjs \
  --samples 20 --repeats 3 --idle-ms 3000 \
  --postgres-image postgres@sha256:9a8afca54e7861fd90fab5fdf4c42477a6b1cb7d293595148e674e0a3181de15 \
  --output /tmp/verfix-37-measurements.json
```

Для одного этапа добавь `--stage files` или `--stage database --storage directory`. В полном прогоне скрипт выбирает хранилище с меньшим p95 короткого ответа при трёх записях по 50 МБ. Оба варианта проходят проверки восстановления до выбора. JSON содержит условия замеров, результаты каждого повтора, интервалы записи, счётчики и сводки. Для проверки стенда за один проход укажи `--samples 1 --repeats 1`.

## Методика

Подставной Telegram отдаёт обновления через `getUpdates`. Контроллер бота вызывает обычный `handleUpdate` и сохраняет состояние с позицией Telegram в одной транзакции. Подставной Codex возвращает детерминированный текст и псевдослучайные байты. Стенд заменяет сеть Telegram и Codex и разбор форматов вложений локальными подставными операциями. Стенд прогоняет сохранение и чтение исходного вложения, передачу байтов в Codex и выдачу файла ответа. [Драйвер](../../scripts/storage-benchmark/driver.mjs) · [Подставные Telegram и Codex](../../scripts/storage-benchmark/bot-child.mjs) · [Транзакции](../../src/store.ts)

Драйвер играет роль внешней стороны Telegram. Он ставит метку в момент публикации обновления и передаёт его в процесс бота по IPC. Ожидание, пока цикл Node.js сможет прочитать обновление в `getUpdates`, входит в замер. Следующие метки фиксируют завершение `accept` и получение текста подставным Telegram. Перед коротким заданием три других пользователя начинают экспорт в свои топики. Драйвер публикует короткое задание по первому событию о начале сохранения. Он учитывает смешанный прогон, когда каждая из трёх записей пересеклась с интервалом ответа и началась до приёма короткого задания. Время совпадает между процессами по монотонным часам Linux. Сценарий с вложением дополнительно измеряет время до получения файла в Telegram.

В каждом прогоне с нагрузкой стенд сначала выполняет один разогревочный раунд. Повтор запускает новый процесс бота и создаёт отдельную базу. Варианты чередуются, данные и сценарии одинаковы. Между раундами стенд очищает данные синтетических диалогов и их файлы. Очистка SQLite обрезает WAL. Таблицы учитывают только рабочие раунды между разогревом и очисткой. PostgreSQL использует один контейнер для этапа. Его WAL включает историю всего кластера, в том числе подготовку и чистку предыдущих прогонов.

p50, p95 и p99 считаются методом ближайшего ранга. Пропускная способность показывает число коротких ответов на секунду суммы измеренных интервалов. Для вложения интервал заканчивается получением файла. При смешанной нагрузке пропускная способность относится к коротким ответам. Время CPU и дисковый ввод-вывод суммируются по процессу бота и cgroup контейнера PostgreSQL. Контейнер использует ресурсы хоста без отдельного лимита CPU или памяти. Пик памяти бота берётся из RSS процесса, включая разогрев, а для PostgreSQL показывается максимум anonymous + shared memory с шагом выборки 10 мс. Измерение I/O отражает счётчики ядра внутри Linux-гостя. Отложенная запись может завершиться за пределами замеряемого окна.

Стенд отдельно замеряет SQL, чтение и запись в каталоге, разбор и сборку JSON. Из общей задержки вычитается только время операций, попавших в её интервал. Остаток включает работу бота, передачу обновления между процессами и задержку планировщика. `monitorEventLoopDelay` измеряет задержку цикла Node.js с разрешением 1 мс. Отдельно записываются время чтения и записи контекста, выборка готовых операций и подтверждение транзакций.

SQLite использует действующую схему и индексы, WAL, `synchronous=FULL` и `secure_delete=ON`. PostgreSQL использует те же запросы, границы транзакций, таблицы и частичные индексы. Типы приведены к `BIGINT` и `BYTEA`, а порядок SQLite `rowid` моделируется столбцом `IDENTITY`. Для PostgreSQL задан таймаут ожидания блокировки 5 с и таймаут запроса 45 с. Настройки записи PostgreSQL включают `fsync=on`, `synchronous_commit=on`, `full_page_writes=on`, `wal_sync_method=fdatasync` и `wal_compression=off`. Подключение одно на процесс бота. PostgreSQL работает через `pg` в потоке Node.js, пока основной поток ждёт ответ. Это измерение реализации с текущим синхронным интерфейсом хранилища. [Адаптер PostgreSQL](../../scripts/storage-benchmark/postgres.mjs) · [Настройки контейнера](../../scripts/storage-benchmark/postgres-server.mjs)

В новых прогонах PostgreSQL также пишет в журнал ожидания блокировки дольше 10 мс. В `lockWaitsByRun` для каждой тестовой БД есть число ожиданий, число отменённых ожиданий и максимальная длительность завершившегося ожидания. Эти счётчики охватывают весь повтор, включая разогрев. [Порог записи ожиданий PostgreSQL](https://www.postgresql.org/docs/18/runtime-config-locks.html)

В варианте с каталогом идентификатор файла из SQLite или PostgreSQL служит ссылкой на локальные байты. Стенд вызывает `fsync` для файла и каталога до подтверждения ссылки в БД. При удалении бот сначала фиксирует удаление ссылки, затем убирает файл. При сбое удаления он сохраняет список для повтора в том же диалоге. После аварии стенд чистит файлы без ссылок при открытии хранилища. Такой порядок рассчитан на одного владельца каталога. PostgreSQL и каталог здесь проверяются на логическое удаление. Для сравнения физической очистки нужны отдельные правила по WAL, резервным копиям и накопителю. [ADR о материалах](../adr/0004-dialogue-file-retention.md) · [Хранилище каталога](../../src/files/payloads.ts)

## Результаты

Эти замеры сделаны на прототипе из коммита `a8ccf75`. Решение для рабочей версии принято в [ADR 0009](../adr/0009-sqlite-and-local-materials.md).

Стенд работал под Linux 6.6.87.2-microsoft-standard-WSL2 на AMD Ryzen 7 5700X3D 8-Core Processor (16 логических CPU, 16 ГиБ RAM). SQLite, каталог и PostgreSQL использовали /dev/sdd ext4. Node.js v26.13.0, SQLite 3.54.0, PostgreSQL 18.4. На вариант пришлось 20 раундов в каждом из 3 повторов. По одному раунду на повтор бот провёл в простое по 3 с.

Драйвер посылает боту `SIGKILL` после вставки записи файла и до подтверждения транзакции. Для каталога он отдельно прерывает сохранение с половиной байтов. После запуска драйвер проверяет, что подтверждённые материалы остались доступны, а незавершённые записи и файлы исчезли. Вложение повторно читается по сохранённому идентификатору без загрузки из Telegram. Из другого топика того же пользователя и из топика другого пользователя бот отклоняет чтение этого файла.

Драйвер прерывает приём обновления между записью позиции Telegram и подтверждением транзакции. После запуска бот видит прежнее состояние и позицию, затем принимает повторно предложенное обновление. При прерывании доставки драйвер ждёт сохранения позиции после первой части. Новый процесс доставляет только файл ответа. Драйвер также проверяет превышение квоты, очистку своего топика через `/new`, отклонение позднего экспорта и подтверждённый `/delete`.

Для резервной копии драйвер останавливает бот, копирует закрытую SQLite или вызывает `pg_dump -Fc`, затем копирует каталог при его наличии. Восстановление открывает новую базу, проверяет позицию Telegram, историю и метаданные и читает материалы из восстановленного диалога с проверкой SHA-256. Время восстановления включает создание базы или копирование, запуск Node.js и обработку сохранённой работы. Каждый сценарий восстановления пройден один раз на вариант. Перезапуск после `SIGKILL` проверяет сбой процесса бота. Прогон с PostgreSQL восстанавливает копию в уже запущенный кластер. [Сценарий восстановления](../../scripts/storage-benchmark/recovery.mjs) · [ADR о топиках](../adr/0006-private-topics-and-deletion.md)

## Решение для #31

Для #31 рекомендую оставить SQLite и рассмотреть локальный каталог для байтов материалов. При четырёх текстовых заданиях p95 ответа был 117 мс у SQLite и 124 мс у PostgreSQL, а пропускная способность составила 34,8 и 33,2 ответа/с соответственно. PostgreSQL быстрее подтвердил одиночную команду на 10,5 мс. К моменту ответа выигрыш составил 3,0 мс.

В обоих вариантах с каталогом основная задержка при записях по 50 МБ пришлась на файловые операции. У SQLite медиана файловой части составила 484 мс из 592 мс короткого ответа. Смена СУБД не убирает синхронную запись файлов из цикла Node.js. На размере 5 МБ каталог улучшил p95 в первом сравнении, а максимальный замер из 60 вырос с 290 до 322 мс.

При переходе с четырёх одновременных текстовых заданий на восемь p95 ответа примерно удвоился у обеих СУБД, а число ответов в секунду осталось около 33. При шестнадцати p95 вырос до 470 мс у SQLite и 491 мс у PostgreSQL. Это граница насыщения в стенде с короткими подставными ответами. Лимит бота для целевого прогона равен четырём, а критерии пользовательской задержки обсуждаются в #27. [Критерии #27](https://github.com/verf1x/telegram-agent/issues/27)

При четырёх заданиях PostgreSQL и бот вместе использовали 67,5 мс CPU за раунд против 11,2 мс у бота с SQLite. PostgreSQL добавляет отдельный процесс, подключение и обслуживание версий кластера. В пробе с 5 МБ материалов копия и восстановление заняли 8 и 143 мс у SQLite с каталогом и 321 и 659 мс у PostgreSQL. Для обоих вариантов с каталогом копия базы и байтов должна относиться к одному моменту. Перед переносом рабочих материалов в каталог понадобится отдельная проверка переноса BLOB и правил очистки.

Вернуться к сравнительному тесту СУБД стоит, если профиль с четырьмя короткими заданиями на целевом хосте дважды покажет p95 приёма выше 80 мс и трассировка отнесёт больше половины задержки к работе БД. Порог 80 мс выбран для повторного замера по наблюдавшемуся p95 приёма 73 мс на SQLite. Ещё один повод появится, если требуемая пропускная способность превысит наблюдавшиеся 33–35 коротких ответов/с. Тогда стоит сравнить варианты под новой нагрузкой и с реальным способом подключения. [Решение #31](https://github.com/verf1x/telegram-agent/issues/31)

В стенде используется подставной Telegram с индикацией набора текста. Штатные черновики добавляют запись `draft_id` на задание, а внешние сервисы добавляют собственные задержки. Абсолютные числа относятся к одному накопителю в WSL2. Для другого хоста нужно повторить замеры. Проверка реального отключения питания требует отдельного эксперимента.
