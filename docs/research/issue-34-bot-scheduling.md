# Фоновая работа Telegram-бота для задачи №34

В Verfix long polling уже ждёт обновлений через `getUpdates`. Нагрузка из задачи №34 возникала в отдельном цикле, который каждые 250 мс читал и разбирал JSON всех диалогов. На рабочем боте замер за 15 секунд простоя показал около 44 МиБ/с по `rchar` и 13% одного ядра. За это окно счётчики физического чтения и записи не выросли. [Задача №34 и исходный замер](https://github.com/verf1x/telegram-agent/issues/34) · [Цикл приёма обновлений Verfix](https://github.com/verf1x/telegram-agent/blob/e9a6cd8fab4f4cc424ea3e12ba64399a723d6700/src/main.ts#L77-L101)

## Как устроены другие боты

- Небольшой `telegram-reminder-bot` запускает aiogram long polling и обработчик напоминаний в одном процессе. Обработчик по умолчанию раз в две секунды выбирает готовые напоминания ограниченной партией через частичный индекс SQLite по `next_attempt_at`. При `429` он записывает новый срок в SQLite. Это пример дешёвого периодического опроса. Код проверен, указанный авторами публичный health-эндпоинт на момент проверки вернул HTTP 404. - Официальный пример `timerbot` совмещает long polling и одноразовые задачи `JobQueue.run_once`. `JobQueue` использует `AsyncIOScheduler`. APScheduler перевыставляет один таймер до ближайшего срока и оставляет цикл без таймера, когда задач нет. Его отдельное SQLAlchemy-хранилище индексирует `next_run_time` и получает ближайший срок через `LIMIT 1`. [Пример timerbot](https://github.com/python-telegram-bot/python-telegram-bot/blob/afb9fc4898a4c84d9766a9b5c9b2bf35da81bd1c/examples/timerbot.py#L68-L104) · [JobQueue](https://docs.python-telegram-bot.org/en/v22.8/telegram.ext.jobqueue.html#telegram.ext.JobQueue.scheduler) · [Расчёт срока](https://github.com/agronholm/apscheduler/blob/6c72a51416893eb0eebbe63d0f2a0151952cab59/src/apscheduler/schedulers/base.py#L1233-L1263) · [Таймер](https://github.com/agronholm/apscheduler/blob/6c72a51416893eb0eebbe63d0f2a0151952cab59/src/apscheduler/schedulers/asyncio.py#L48-L62) · [SQL-хранилище](https://github.com/agronholm/apscheduler/blob/6c72a51416893eb0eebbe63d0f2a0151952cab59/src/apscheduler/jobstores/sqlalchemy.py#L74-L105)

## Когда растёт нагрузка

Telegram Bot API доставляет входящие обновления через `getUpdates` или HTTPS-вебхук. Это выбор транспорта. Например, grammY Runner обрабатывает обновления параллельно даже на long polling и умеет сохранить последовательность для заданного ключа. При нескольких процессах обработку исходящих задач можно отдать общей очереди. [Telegram Bot API](https://core.telegram.org/bots/api#getting-updates) · [Параллельная обработка grammY](https://grammy.dev/plugins/runner)

В Redis-реализации BullMQ воркер ждёт через блокирующий `BZPOPMIN` с ограниченным таймаутом. Метка в Redis хранит срок ближайшей отложенной задачи. BullMQ поддерживает повторы с задержкой и общий лимит отправки для воркеров одной очереди. В продакшене Redis требует настройки сохранения данных. Потерянный ответ Telegram после `sendMessage` по-прежнему требует решения на стороне приложения. [Ожидание воркера](https://github.com/taskforcesh/bullmq/blob/ba63962a39388be8f061f6335a750330a4ab9a1c/src/classes/worker.ts#L861-L937) · [Блокирующий вызов](https://github.com/taskforcesh/bullmq/blob/ba63962a39388be8f061f6335a750330a4ab9a1c/src/classes/redis-queue-backend.ts#L2838-L2851) · [Метка ближайшего срока](https://github.com/taskforcesh/bullmq/blob/ba63962a39388be8f061f6335a750330a4ab9a1c/src/commands/includes/addDelayMarkerIfNeeded.lua#L8-L15) · [Повторы](https://docs.bullmq.io/guide/retrying-failing-jobs) · [Лимиты](https://docs.bullmq.io/guide/rate-limiting) · [Сохранение данных Redis](https://docs.bullmq.io/guide/going-to-production#persistence) · [ADR о рассылке Verfix](../adr/0007-broadcast-delivery.md)

## Применение в Verfix

1. Использовать текущую SQLite и один процесс. В той же транзакции, что и состояние диалога или рассылки, записывать компактные метаданные фоновой операции с адресом топика или идентификатором рассылки и ближайшим сроком. При приёме обновления фиксировать их вместе с `offset`. Построить метаданные старых записей при миграции. Занятость для общего лимита проверять по метаданным и действующим заданиям. [Задача №34](https://github.com/verf1x/telegram-agent/issues/34) · [Транзакции SQLite](https://sqlite.org/lang_transaction.html) · [Приём обновления в Verfix](https://github.com/verf1x/telegram-agent/blob/e9a6cd8fab4f4cc424ea3e12ba64399a723d6700/src/store.ts#L209-L224) · [Семантика `offset`](https://core.telegram.org/bots/api#getupdates)
2. Будить обработчик при запуске, после сохранения новой работы и в ближайший срок. По индексу выбирать готовые операции и следующий срок, читать JSON только у нужного топика. При появлении более ранней операции перевыставлять `setTimeout`. При пустой очереди фоновый обработчик ждёт сигнала без запросов к базе. Брать начальный `offset` из SQLite при запуске и обновлять его копию в памяти после фиксации транзакции, чтобы пустой цикл `getUpdates` обходился без чтения базы. [Индексы SQLite](https://sqlite.org/queryplanner.html#_searching_and_sorting_at_the_same_time) · [Таймеры Node.js](https://nodejs.org/api/timers.html#settimeoutcallback-delay-args) · [Семантика `offset`](https://core.telegram.org/bots/api#getupdates)
3. Для явного `429` сохранять абсолютный срок, рассчитанный по `retry_after`, и позицию доставки. После перезапуска продолжать с оставшихся частей ответа и получателей. Для потерянного ответа при рассылке использовать статус «доставка неизвестна», как в ADR. При запуске проверять текущий список доступа до возобновления отправки. [Telegram `retry_after`](https://core.telegram.org/bots/api#responseparameters) · [ADR о рассылке](../adr/0007-broadcast-delivery.md)

Решения о чтении `.env` и обработке нечитаемого диалога зафиксированы в ADR. [ADR о фоновых операциях](../adr/0008-event-driven-background-work.md)

## Проверка результата

- Сравнить по минуте простоя до и после на одинаковых синтетических базах с короткой и тяжёлой историей, с подставными Telegram и Codex. После запуска, когда сообщений и активных заданий нет и ни один срок не наступил, ожидание обновлений обходится без запросов к SQLite и повторных чтений `.env`. Число фоновых операций не растёт с размером истории. Записать CPU, `syscr`, `rchar`, `read_bytes` и `write_bytes`.
- Проверить, что одна готовая операция читает только состояние своего топика, более ранняя операция переносит пробуждение, а временный сбой повторяется в срок без нового сообщения. Проверить сохранение порядка частей ответа и отсутствие повторной отправки подтверждённых частей и получателей.
- Проверить обновление старой базы, перезапуск при отложенном `429` и при незавершённой рассылке, сбросе или удалении. Проверить очистку предпросмотров, привязку прежнего диалога, параллельные топики, отмену и штатную остановку.
- Проверить, что бот применяет изменённый список доступа при запуске и продолжает работу других топиков при нечитаемом состоянии одного диалога. Состояние проблемного топика сохраняется, а в журнале появляется сообщение об ошибке без истории. [Приёмка задачи №34](https://github.com/verf1x/telegram-agent/issues/34)
